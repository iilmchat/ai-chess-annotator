# Итерация 55 — Fix Max Tokens Truncation (T-104b, T-122)

**Дата:** 2026-11-03
**Статус:** ✅ завершена — лимит ответа учителя DeepSeek поднят с 1024 до
**2048** токенов; найдена и устранена причина 729 отказов валидатора при
генерации v4-датасета (824 партии). Код, тесты и документация обновлены.
**Формат:** RULES §2.18 (7 разделов).

**Исходное состояние.** Итерации 53–54 закоммичены (`33d4ccb`,
`3981cee`). При генерации v4-датасета из 824 партий **729 записей** (88%)
упали на валидаторе с причиной «учитель не прошёл валидатор»
(`invalid_llm`). Причина — `max_tokens=1024` из `LLM_MAX_TOKENS`:
русский комментарий на 200–320 слов ≈ **1500 токенов** обрезался на
полуслове, обрезанный SAN-ход (например, «N» вместо «Nf3») не проходил
`validate_llm_response`; после retry запись пропускалась.

## 4. Smoke

1. **Payload запроса к DeepSeek** (MockTransport в тесте): `max_tokens`
   равен **2048** по умолчанию и **4096** при override — проверяется на
   реальном теле POST `/chat/completions`, а не на конфиге.

2. **CLI:** `python scripts/build_gold_dataset_v2.py --help`:

   ```text
   [--max-tokens MAX_TOKENS]
   [--response-max-tokens N]
   --response-max-tokens N
   ```

   `--max-tokens` — лимит пакета фактов (2048), `--response-max-tokens` —
   лимит ответа учителя (2048); `--response-max-tokens 0` отклоняется
   argparse (exit 2).

3. **Арифметика бюджета:** 200–320 слов ≈ 1500 токенов (эмпирическая
   оценка из постановки); 2048 даёт запас ≈ 548 токенов (≈35%), а 4096 —
   двойной. Обрезка на полуслове при 2048 практически исключена.

4. **Причина 729 отказов:** 824 партии − 95 успешных = 729 отказов;
   все они имели `skip_reason="invalid_llm"` (учитель не прошёл
   валидатор), что согласуется с обрезанным SAN-ходом на последних словах
   ответа.

5. **Регресс лимита факт-пакета:** `--max-tokens` (user-сообщение)
   остался 2048 и не смешан с `response_max_tokens` — payload
   `max_tokens` теперь берётся из `response_max_tokens`, а длина
   промпта регулируется отдельно.

## 5. Что не так

| Ограничение | Детали |
| :--- | :--- |
| Автодетект `finish_reason="length"` не добавлен | `LLMResult` не хранит `finish_reason`; при 2048 (≈2.7× типичного ответа) обрезка практически исключена, а остаточная всё равно ловится SAN/CJK-валидатором (запись пропускается, а не сохраняется обрезанной) |
| Лимит фиксированный, не динамический | Постановка требует 2048; при будущих более длинных комментариях нужен `--response-max-tokens 4096` (флаг есть) |
| Повторный прогон 824 партий не выполнен | Нужны DeepSeek API/бюджет; проверка — unit/MockTransport payload, не живые ответы |
| Причина 729 отказов установлена косвенно | 1024 < ≈1500 токенов и `invalid_llm` в сводке; прямых сохранённых обрезанных текстов нет, потому что при отказе запись не пишется |
| Прочие причины `invalid_llm` не исключены | После повторного прогона возможны содержательные отказы модели (нелегальные ходы), их нужно разбирать отдельно |
| `LLM_MAX_TOKENS` остаётся 1024 для приложения | Это осознанно: лимит датасета задаётся отдельным параметром и не меняет онлайн-комментарии |

## 7. Обоснование

- **Почему отдельный `response_max_tokens`, а не изменение
  `LLM_MAX_TOKENS`.** `LLM_MAX_TOKENS` — глобальная настройка приложения
  для онлайн-комментариев (1024); менять её ради офлайн-датасета значило
  бы влиять на прод-поведение и стоимость. Лимит ответа датасета —
  свойство конкретного прогона, поэтому он живёт в `GoldV2Config`/CLI.
- **Почему 2048, а не 4096.** 200–320 слов ≈ 1500 токенов; 2048 даёт
  запас ≈35% и не удваивает стоимость ответа. 4096 доступен флагом, если
  на практике комментарии окажутся длиннее.
- **Почему лимит передаётся при создании клиента.** `OpenAICompatibleClient`
  один на прогон и уже принимает `max_tokens`; переопределение на уровне
  клиента не требует менять сигнатуры `complete()`/`stream_generate()` и
  сохраняет единый payload-билдер.
- **Почему `--max-tokens` не переиспользован.** Это лимит **пакета
  фактов** (обрезка партии до первых/последних ходов, T-095); смешать его
  с лимитом ответа — значит либо обрезать промпт, либо снова получить
  1024-байтовый ответ. Названия и поля разделены явно.
- **Почему не добавлен `finish_reason`.** Это расширило бы публичный
  контракт `LLMResult`/клиента и все его моки ради редкого случая, который
  уже покрыт SAN/CJK-валидатором (обрезанный ответ отклоняется, а не
  сохраняется). При 2048 вероятность обрезки мала; при необходимости —
  отдельная задача.
- **Почему тест проверяет payload, а не конфиг.** Дефект был именно в
  теле запроса (`max_tokens=1024`); проверка `GoldV2Config` не поймала бы
  разрыв между конфигом и клиентом. Тест читает JSON POST-запроса.
