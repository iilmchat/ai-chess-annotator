## 2. Замеры реального движка (до написания кода)

Сырой UCI-прогон Stockfish 17.1 (`D:\Tools\stockfish\stockfish.exe`),
стартовая позиция, MultiPV 3:

| Команда | Итог |
| :--- | :--- |
| `go depth 5` | 6 мс, глубина 5 по всем линиям |
| `go depth 12` | **190 мс**, глубина 12 (укладывается в бюджет 200 мс «новичка») |
| `go depth 18 movetime 1000` | **1002 мс**, достигнута глубина **16**, дальше стоп по времени |
| `go depth 20 movetime 1000` | 1002 мс, глубина 17 |

Вывод: на этой машине depth 18 за 1 с **не достигается** — бюджет времени
реально ограничивает глубину. Это ожидаемое поведение (`go depth N
movetime T` — стоп по первому событию), но оно означает:

1. «Клуб» ≈ 1.00 с на позицию (а не «depth 18 за 0.3 с»);
2. бенчмарк-тест должен допускать IPC-оверхед поверх 1000 мс (≈ +15 мс),
   иначе он флакует;
3. полная партия 40 ходов × 1 с ≈ 41 с > 30 с из SPEC §9 — заведён
   **KI-014** (пул движков/кэш/критические ходы — решение в T-009).

## 3. Почему свой UCI-клиент, а не библиотека `stockfish`

Проверен `stockfish` 5.2.0 (уже в зависимостях):

| Требование | Что даёт библиотека |
| :--- | :--- |
| PV-линии (`EngineLine.pv`) | ❌ `get_top_moves()` возвращает только ход + cp/mate, без PV |
| `multipv`-ранг и `depth` на линию | ❌ нет в публичном API |
| Таймаут поиска + перезапуск | ❌ только `_go`/`_read_line` (приватные), без управления |
| Не блокировать event loop | ❌ sync `subprocess` (нужен `to_thread`, но процесс один и он всё равно сериализует) |

Итог: собственный `_UciEngine` (~150 строк): `asyncio.create_subprocess_exec`,
`asyncio.Lock` на сервис, `asyncio.wait_for` на каждое чтение, `quit`/`kill`
при закрытии, полный перезапуск процесса после таймаута.

Совет из постановки про `asyncio.to_thread` **не применяется**: без потока
код проще, таймауты точнее, а GIL-вопрос снимается — процесс движка
внешний.

## 4. Границы контракта

1. **Оценки `EngineLine`** — с точки зрения стороны, которая делает ход
   (конвенция UCI). Иначе MultiPV-линии нельзя сравнивать между собой.
2. **`MoveAnalysis.eval_before/eval_after`** — приведены к точке зрения
   **сделавшего ход** (плюс = хорошо для него): аннотация читается как
   «сколько ты потерял».
3. **Мат** кодируется как `±(10000 − 100·N)`, иначе `delta_cp` с матом
   несравним с обычными сантипешками.
4. **`delta_cp = max(0, eval_before − eval_after)`**: отрицательная дельта
   возможна только из-за разной глубины поисков, и «выигрыш относительно
   лучшей линии» — шум, а не улучшение.
