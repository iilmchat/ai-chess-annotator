1. **CLI:** `python scripts/build_gold_dataset_v2.py --help` показывает
   `[--timeout-s SECONDS] [--append]` и подписи флагов; `--timeout-s 0`

2. **Timeout-сценарий (MockTransport):**

   ```text

   [timeout] deepseek: таймаут 30 с; повтор 2/3 через 0.0 с
   [timeout] deepseek: таймаут 30 с; повтор 3/3 через 0.0 с
   [timeout] deepseek: таймаут 30 с после 4 попыток — запись пропущена
   ================= 7 passed, 36 deselected =================
   ```

   Первая позиция пропущена (`skipped["timeout"] == 1`), вторая
   сгенерирована (`converted == 1`); в файле ровно одна запись (`p2`).

3. **Crash-сценарий:** первая позиция записана и `flush()`-нута, вторая
   падает с сетевой ошибкой (`LLMError`), но в файле остаётся **1 строка**
   — прогресс не потерян.

4. **Append-сценарий:** прогон с `--limit 1` → 1 строка; повторный запуск
   с `--append` → 2 строки, первая строка не изменилась, сгенерирована
   только недостающая позиция (1 API-вызов), `already_done == 1`.

5. **Ручная проверка инкрементальности** на временном каталоге: при
   `dataset_writer.write(record)` файл сразу содержит строку (видно
   `Get-Content` до закрытия writer) — `flush()` вызывается на каждой
   записи.

## 5. Что не так

| Ограничение | Детали |
| :--- | :--- |
| Retry только на таймауты | Прочие ошибки (сеть/HTTP/кривой ответ) по-прежнему роняют прогон — это осознанно, чтобы не маскировать реальные сбои; 5xx уже ретраит `OpenAICompatibleClient` |
| `--append` опирается на `metadata.id` | Для PGN id = `file.pgn:N`, для позиций — id из JSONL. Если входные файлы переупорядочить/заменить, id могут сместиться → часть записей сгенерируется повторно, часть пропустится |
| Пропуск таймаута теряет запись | После 4 неудачных попыток позиция не попадает в датасет; в сводке это видно (`таймаутов (запись пропущена)`), но при массовых таймаутах датасет будет неполным |
| Задержка на пропуск | Каждый таймаут может добавить до ~14 с пауз (2+4+8) плюс сами таймауты; при системных проблемах прогон замедляется, но не падает |
| Пустой файл не остаётся | При нуле записей и `--append=False` writer удаляет созданный пустой файл ради совместимости со старым поведением; при падении до первой записи пустой файл может остаться — это ожидаемо |
| Живой DeepSeek не вызывался | Проверка — `MockTransport` + unit; реальный API/бюджет не тратились, поэтому фактическая частота таймаутов не измерена |
| DeepSeek-клиент уже оборачивает `httpx.TimeoutException` | В `OpenAICompatibleClient` таймаут приходит как `LLMTimeoutError`; перехватываем оба типа, чтобы обёртки/фейки в тестах и будущие клиенты не ломали поведение |
| Независимый verifier-агент недоступен | Аудит итерации 54 выполнен Lead'ом (тесты/ruff/mypy/smoke); агент-verifier завершался с ошибкой без отчёта, это зафиксировано в финальном ответе |

## 7. Обоснование

- **Почему 3 retry и экспоненциальная пауза 2/4/8 с.** Один таймаут
  DeepSeek — обычно временная перегрузка; три повтора с растущей паузой
  переживают короткий сбой, но не растягивают прогон бесконечно. Суммарно
  до 4 вызовов на запись, как в постановке («до 3 retry»).
- **Почему ловим и `LLMTimeoutError`, и `httpx.TimeoutException`.**
  Продакшен-клиент уже преобразует `httpx.TimeoutException` в
  `LLMTimeoutError` (`_post_with_retries`), но тесты/фейки и другие
  обёртки могут бросать httpx-исключение напрямую; двойной `except` делает
  retry-политику независимой от реализации клиента.
- **Почему пропуск, а не остановка.** Один проблемный запрос не должен
  обнулять сотни уже сгенерированных записей; `skipped_timeout` попадает в
  сводку, и решение о догоне принимается по данным, а не по факту падения.
- **Почему `DatasetWriter`, а не `write_records` в конце.**
  Инкрементальная запись + `flush()` — единственный способ сохранить
  прогресс при падении процесса; writer также инкапсулирует режим
  `--append` и загрузку готовых id.
- **Почему `--append` по `metadata.id`, а не по числу строк.** Число строк
  не говорит, какие именно записи готовы; id (позиция/файл:номер) —
  стабильный ключ, по которому можно пропустить уже сгенерированное и не
  наплодить дублей. Ограничение при изменении входов зафиксировано в §5.
- **Почему перезапись по умолчанию сохранена.** `--append` — явный флаг:
  старые сценарии (полный перегенерировать) остаются прежними, а resume —
  осознанный выбор оператора. Это же объясняет удаление пустого файла при
  нуле записей: старые тесты и пользователи ожидают отсутствие файла.
- **Почему не ретраим прочие ошибки.** Иначе неверный ключ/модель/формат
  выглядели бы как «временный сбой» и бесконечно замедляли прогон;
  таймаут — единственный класс, где повтор безопасен и осмыслен.
