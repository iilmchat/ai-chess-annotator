# Итерация 53 — SSE CJK Buffer Filter (KI-060, T-120)

**Дата:** 2026-11-03
**Статус:** ✅ завершена — SSE-комментария больше не пропускает китайские
иероглифы: добавлен буферизующий `CjkStreamBuffer`, очищенный текст
отдаётся в `delta` и сохраняется в БД; KI-060 остаётся **Open**
(chat-SSE, диапазон U+4E00–9FFF, v4 500+).
**Формат:** RULES §2.18 (7 разделов).

**Исходное состояние.** В итерации 52 зафиксированы результаты v3-PGN
(3.67/10, CJK 0.00%) и закрыт KI-061; KI-060 оставался Open с явным
остатком: обычный ответ сервиса чистится от CJK (итерация 49), но
`app/commentary/streaming.py` отдавал чанки LLM в `delta` напрямую, поэтому
иероглиф уходил клиенту мгновенно. Параллельно генерируется v4-датасет
(200 PGN-партий, цель 500+), но фильтр нужен независимо от качества модели.

## 4. Smoke

1. **Unit-сценарий «CJK между чистыми»:**

   ```python
   buffer = CjkStreamBuffer()
   chunks = ["Партия ", "началась с d4. ", "这是中文。", "Затем ", "последовало Nf6."]
   deltas: list[str] = []
   for chunk in chunks:
       deltas.extend(buffer.feed(chunk))
   deltas.extend(buffer.flush())
   # → ["Партия началась с d4. ", "Затем последовало Nf6."]
   # ни один delta не содержит U+4E00–9FFF
   ```

## 5. Что не так

| Ограничение | Детали |
| :--- | :--- |
| **Chat-SSE не фильтруется** | `app/chat/streaming.py` по-прежнему отдаёт `delta` и cache-hit без CJK-фильтра — отдельный остаток KI-060 (T-120 закрыт только для комментария) |
| **Диапазон только U+4E00–9FFF** | Кана, хангыль, Ext-A/B, compatibility ideographs и fullwidth-формы не вырезаются: расширение диапазона изменило бы и не-стримовое поведение; зафиксировано в KI-060 |
| **В стриме нет retry и порога `CJK_MAX_SHARE`** | Текст уже показан клиенту — переспрашивать поздно; ответ очищается, а не отклоняется. CJK-доля в стриме не отклоняется (в отличие от `_generate_with_validation`), CJK-only ответ → `llm_empty` |
| **SAN-валидация — по очищенному тексту** | Нелегальный ход, «спрятанный» в вырезанном CJK-предложении, не валидируется и не показывается. Это осознанное расхождение с сервисом (тот валидирует исходный ответ до вырезания) |
| **TTFT вырос** | Первый `delta` ждёт конца предложения или 20–30 символов; для мгновенного стрима пришлось бы рисковать утечкой CJK-предложения |
| **Legacy-кэш не инвалидируется** | Грязная cache-запись очищается при каждом hit, но не перезаписывается: при повторных запросах очистка выполняется снова (дёшево, но не идеально) |
| **Исключение посреди стрима** | `flush()` не вызывается, хвост буфера теряется; утечки нет (буфер не эмитился), но часть текста не доедет — стрим всё равно терминален ошибкой |
| **Нет живого прогона на 7B** | Проверка — мок-LLM + unit; реальный LM Studio в этой итерации не вызывался (v3 0.00% CJK по eval итерации 52) |
| **Eval-метрика не знает про стрим** | `evaluate_llm.py` считает только тексты `commentaries`; отдельного «CJK-в-SSE» теста в eval нет — фильтр покрыт unit/integration |

## 7. Обоснование

- **Почему буфер в `app/commentary/streaming.py`, а не в общем
  `app/streaming.py`.** Задача итерации — комментарий; общий модуль SSE не
  знает про CJK-политику. Класс рядом со стримом проще тестировать и
  переносить в чат отдельным шагом (T-120/остаток KI-060).
- **Почему границы предложения, а не просто «кусок 20–30 символов».**
  Иероглиф может стоять в середине предложения; отдавать чистый префикс
  предложения, а хвост с CJK вырезать — значит показать клиенту обрывок
  фразы. Буферизация до терминатора позволяет вырезать предложение целиком
  (как `service.py`) и не выдавать «полуфразу».
- **Почему CJK-терминаторы безусловны, а латинские — только перед
  пробелом.** В китайской типографике после `。` пробела может не быть;
  без безусловной границы пришлось бы ждать 30 символов. Латинские `.`
  внутри `1.20`/`e.g.` не должны дробить текст.
- **Почему в стриме вырезаем, а не отклоняем по `CJK_MAX_SHARE`.** Retry
  после показанного текста недопустим (в стриме его и так нет), а
  отклонение всего ответа дало бы `error` после уже отправленных дельт.
  Компромисс: очищаем и логируем счётчики; CJK-only ответ всё равно
  отклоняется (`llm_empty`), потому что показывать нечего.
- **Почему ограничиваем буфер `MAX_DELTA_CHARS`.** Иначе длинный CJK-ран
  без пунктуации копился бы до конца ответа (OOM/задержка), а наивный
  «flush по размеру» отдал бы иероглифы. Ограниченный буфер режет по
  словам, затем каждый кусок всё равно проходит `has_cjk`.
- **Почему чистим cache-hit.** Кэш мог сохранить текст до итерации 49;
  статическая запись с CJK должна быть либо очищена, либо не использована.
  Выбрано: `sanitize_cjk` (частичный дрейф → вырезать), при rejected —
  регенерация; это дешевле инвалидации всего кэша.
- **Почему тесты используют независимый регэксп.** Проверка «нет CJK» тем
  же `has_cjk`, который фильтр и применяет, могла бы скрыть ошибку; в
  integration-тестах используется собственный `[\u4e00-\u9fff]`.
