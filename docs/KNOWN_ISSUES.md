# Known Issues — ChessAnnotator

Реестр известных проблем, ограничений и отклонений окружения.
Формат записи (`RULES.md` §9.2):

```
## KI-NNN · Open|Closed · Low|Med|High|Critical · <модули>
**Симптом.** …
**Причина.** …
**Обход / текущее поведение.** …
**План закрытия.** …
```

Правило: любое отклонение — здесь. «Замазать» молча (широкий `except`,
`--passWithNoTests`, отключённый линтер) запрещено: запись в реестр
обязательна.

## KI-001 · Open · Low · infra, dev-env

**Симптом.** `docker compose up -d postgres redis` падает:

```
Error response from daemon: ports are not available: exposing port TCP
127.0.0.1:6380 -> 127.0.0.1:0: listen tcp4 127.0.0.1:6380: bind: Only one
usage of each socket address (protocol/network address/port) is normally permitted.
```

**Причина.** На dev-машине `127.0.0.1:6380` уже опубликован контейнером
`ticket-redis` другого проекта (`0.0.0.0:6380->6379/tcp`).

**Обход / текущее поведение.** Порт Redis в `docker-compose.yml` —
`"127.0.0.1:${REDIS_PORT:-6380}:6379"`. Канон 6380 сохранён (CI, прод,
чистые машины), локально в `.env` задано `REDIS_PORT=6381` и
`REDIS_URL=redis://127.0.0.1:6381/0`. `docker compose ps` показывает
`6379/tcp` → `127.0.0.1:6381`, healthcheck `redis: ok`.

**План закрытия.** Не требует кода. При освобождении 6380 — убрать
`REDIS_PORT` из локального `.env`. В прод-стеке порт наружу не
публикуется вовсе.

**Обход / текущее поведение.** Живая проверка healthcheck выполнена на

**План закрытия.** Освободить 8000 (остановить чужой контейнер) либо
сделать порт API настраиваемым (`API_PORT` + переменная прокси в Vite) —
кандидат в T-019.

## KI-003 · Open · Low · db, migrations

**Симптом.** После `alembic downgrade base` расширение `vector` остаётся
установленным в БД.

**Причина.** `downgrade` миграции `b802598c3778` намеренно не делает
`DROP EXTENSION vector`: расширение — свойство базы, а не схемы; в
общей БД им могут пользоваться другие схемы, а `DROP EXTENSION ... CASCADE`
удалил бы чужие объекты.

**Обход / текущее поведение.** `downgrade base` возвращает только схему
`public` к состоянию «нет таблиц» (проверено), тип `level` удаляется.
Для полностью чистой БД — `docker compose down -v`.

**План закрытия.** Не планируется; при необходимости — отдельная
административная команда вне Alembic.

## KI-004 · Open · Low · api, typing

**Симптом.** `mypy app`:

```
app/api/v1/health.py: error: Call to untyped function "from_url" in typed context
```

**Причина.** `redis-py` 5.3 поставляет `py.typed`, но `Redis.from_url`
в inline-типах остаётся без аннотаций (upstream-пробел). Стабы
`types-redis` 4.6 не помогают: они описывают redis 4.x и не знают
`aclose`.

**Обход / текущее поведение.** В `app/api/v1/health.py` узкий
`# type: ignore[no-untyped-call]` с комментарием; `types-redis` удалён из
dev-зависимостей.

**План закрытия.** Убрать ignore, когда redis-py аннотирует `from_url`
(проверять при обновлении `redis`).

## KI-012 · Open · Med · ingestion

**Симптом.** `parse_pgn("1. e4 e5 2. Zz9 *")` возвращает партию из

**План закрытия.** Перед `read_game` (или после) проверять, что весь
movetext разобран: сравнить количество SAN-токенов с числом полуходов

## KI-014 · Closed · Med · engine, api

**Симптом.** `analyze_game_moves` на уровне «клуб» анализирует **каждую**
позицию (`N + 1` поисков по ~1 с). Для партии из 40 ходов это ≈ 41 с, а
SPEC §9 требует `/v1/analyze` ≤ 30 с (уровень «клуб»).

**Причина.** Оценка «до/после» берётся из отдельных поисков движка (по
одному на позицию). Это самый точный, но и самый дорогой способ; пула
движков и кэша не было.

**Решение (T-009).** `app/engine/pool.py` — `EnginePool`: 4 независимых
процесса Stockfish + очередь свободных (`asyncio.Queue`), анализ всех
позиций параллельно через `asyncio.gather`. Каждый процесс имеет свой
wall-clock бюджет `movetime`, поэтому время ≈ `ceil(N / pool_size) × 1 с`.

**Доказательство.** `tests/integration/test_api_analyze.py`:
партия `example.pgn` (53 полухода) на уровне «club» через `/v1/analyze` —
**14 646 мс** (лимит 30 000 мс), тест падает при превышении SLA. Полный
прогон тестов — 26 с вместе с этим тестом.

**Остаточное ограничение.** Для партий длиннее ~160 полуходов 30 с
не гарантируются (линейный рост) — вынесено в KI-017.

**Симптом.** Валидатор (T-015) проверяет только **легальность** SAN-ходов.
Он не проверяет, что модель правильно приписала оценку, мотив или «лучший
ход» конкретному полуходу. Пример из живого прогона (итерация 7): модель
пишет «движок рекомендует Qe7 вместо e4» — ходы легальны, но атрибуция
рекомендации может не совпадать с пакетом фактов.

**Причина.** Семантическая проверка требует сопоставления утверждений
текста с фактами (JSON-пакетом), а не только доски. Это отдельный
NLI/rule-слой, которого пока нет.

**Обход / текущее поведение.** Промпт жёстко требует «не менять оценки» и
«использовать только ходы из пакета», а валидатор отбрасывает выдуманные
ходы. Оценки в тексте остаются на ответственности промпта. В итерации 16
добавлен узкий фильтр: одиночная клетка (`e1`, `a4`), нелегальная во всех
позициях партии, больше не считается ходом — иначе фразы «король на e1»
давали ложный 502. Семантическая проверка атрибуции по-прежнему не
сделана.

**Прогресс (итерация 37).** Добавлен семантический слой
`app/commentary/semantic.py`: утверждения «фигура X на поле Y» и
«связка фигуры Z» (RU+EN) сверяются с позициями партии и PV-линиями
движка; неверное утверждение ведёт к retry с подсказкой, а на последней
попытке offending-предложения вырезаются вместо 502. Флаг
`SEMANTIC_VALIDATION_ENABLED`. Остаётся открытой **атрибуция оценок,
мотивов и «лучшего хода»** к полуходам, а также геометрия связки и
привязка утверждения к конкретному полуходу (утверждение валидно, если
верно хотя бы в одной позиции партии).

**План закрытия.** T-016/T-023: сверять числа в тексте (±cp, «мат в N») с
фактами ключевых моментов; при расхождении — retry с уточнением или
вырезание фразы. Плюс метрика «доля верных атрибуций» на 30–50 партиях.

## KI-031 · Closed · Med · api, finops, security

**Симптом.** Дневной лимит токенов зависит от тира `free`/`pro`, а тир
брался из заголовка `X-User-Tier`. Любой клиент мог прислать
`X-User-Tier: pro` и получить лимит 500 000 вместо 50 000.

**Причина.** Публичный API пока без JWT/ролей (Фаза 5/T-028); сервер не
знает, кому доверять. IP-адрес тоже подделывается через
`X-Forwarded-For`, если приложение стоит не за доверенным прокси.

**Решение (T-033, итерация 18).** Заголовки `X-User-Tier`/`X-User-Id`
больше не читаются. Тир — только `pro` для IP из `PRO_IPS` (CSV), иначе
`free`. `X-Forwarded-For` учитывается только при
`TRUST_FORWARDED_FOR=true`, то есть за явно настроенным прокси; иначе
берётся адрес сокета. Тест `test_user_tier_header_is_ignored`
подтверждает, что подделка игнорируется.

**Остаток.** JWT-тир (`sub`/`role`) — T-028/T-031b; до этого `PRO_IPS`
должен быть статическим белым списком доверенных адресов.

## KI-033 · Closed · Med · audit, admin

**Симптом.** Аудит правки промпта писался в `after_edit_committed`, то
есть **после** commit самой правки и в отдельной транзакции. Если запись
аудита падала, правка промпта уже была сохранена, а событие терялось.

**Причина.** `starlette-admin` коммитит транзакцию до вызова
`after_edit_committed`; вставить аудит в ту же транзакцию без обхода
`DBSessionMiddleware` нельзя.

**Решение (итерация 19).** Аудит перенесён в `PromptAdmin.after_edit`:
он вызывается **до** commit, использует `request.state.session` и пишет
`audit_logs` в той же транзакции, что и `prompts`. При сбое
`append_audit` исключение уходит в `_render_edit`, ответ становится 4xx,
`DBSessionMiddleware` откатывает и правку, и аудит. Тесты:
`test_after_edit_writes_audit_in_same_session`,
`test_after_edit_propagates_audit_failure`; smoke
`ITERATION-19_prompt_audit_smoke.log` (action `prompt.update`, chain OK).

**Остаток.** Для injection аудит по-прежнему отдельная best-effort
транзакция: запрос завершается 422, и откатывать нечего. Это осознанно.

## KI-034 · Open · Med · cache, llm

**Симптом.** Semantic-поиск кэша идёт по FEN первого ключевого момента
(комментарий) или финальной позиции (чат) и `prompt_hash` из
уровня/модели/системного промпта/style/question. В `prompt_hash` нет
ходов партии, поэтому две разные партии с близким FEN (< 0.05) и
одинаковым стилем могут получить один и тот же текст. Для комментария
это особенно рискованно: текст может упоминать ходы чужой партии.

**Причина.** Схема из постановки использует `fen_hash`/`fen_embedding` и
`prompt_hash`, но не `analysis_hash` всей партии. Exact-хит безопасен
(`fen_hash+level+prompt_hash`), semantic — эвристика.

**Обход / текущее поведение.** Порог 0.05 консервативен; exact ищется
первым; `prompt_hash` включает style/question. В eval кэш выключен.
Кэш-хит помечается `model=semantic-cache`, `tokens_used=0`.

**План закрытия.** T-032b: включить в ключ `analysis_hash`/`pgn_hash`
(или хранить `commentary_id` и проверять совпадение партии) для
семантических хитов; для engine-кэша оставить FEN. Добавить тест на
«похожий FEN, но другая партия» и, при необходимости, режим
`semantic_only_for_engine`.

## KI-035 · Closed · High · web, api

**Симптом.** `GET /v1/games?limit=20` возвращал последние партии всех
пользователей: id, имена, турнир, уровень. Отдельного владельца у
`games` не было, auth/JWT не внедрён (T-028). Страница `/history`
показывала этот глобальный список, то есть любой клиент мог перебрать
чужие партии и открыть `/analysis/:id`.

**Причина.** MVP без пользовательских аккаунтов: `games.user_id`
существовал, но никогда не заполнялся; `GET /v1/games/{id}` был
публичным по id.

**Решение (KI-035, итерация 24 / T-041).**

- **JWT-аутентификация:** `app/auth/` (passlib/bcrypt + python-jose),
  `POST /auth/register|login|refresh`, `GET /auth/me`; access 15 мин,
  refresh 7 дней; зависимости `get_current_user` / `require_admin`.
- **Схема (миграция `c7d8e9f0a1b2`):** `users.role` (enum `admin_role`:
  user/admin/auditor), `is_active`, `password_hash`, `last_login_at`;
  `commentaries.user_id`, `edits.user_id`; индексы
  `ix_games_user_id_created`, `ix_users_role`, `ix_commentaries_user_id`,
  `ix_edits_user_id`.
- **Изоляция:** `POST /v1/analyze` пишет `games.user_id = current_user.id`;
  `GET /v1/games` — только свои (admin — все, legacy NULL-owner — только
  admin); `GET /v1/games/{id}` — чужой id неотличим от несуществующего
  (404); `POST /v1/commentary(/stream)` и `POST /v1/chat(/stream)` —
  проверка доступа к партии **до** любого вызова LLM; `PATCH
  /v1/commentaries/{id}` — проверка владельца и `edits.user_id`;
  `commentaries.user_id` заполняется и для SSE-стрима.
- **Usage:** аутентифицированный admin/auditor → tier `pro`, user →
  `free`, subject `user:{id}`; анонимно — прежний IP-путь.
- **Фронтенд:** `/login` (вход/регистрация), токены в `localStorage`,
  Bearer-заголовок + single-flight refresh на 401, route guard, профиль и
  «Выйти» в шапке.

**Доказательство.** `tests/unit/test_auth.py` (24) +
`tests/integration/test_auth_api.py` (15, real auth) — регистрация/вход/
refresh/me, 401/403/409/422. `tests/integration/test_data_isolation.py`
(11) — матрица доступа user A/user B/admin для list/get/commentary/chat/
patch, legacy NULL-owner только admin, 401 анонимно.
`tests/integration/test_usage_roles.py` (4) — роли и тиры. Полный suite:
382 passed, 1 skipped, 1 xfailed. Живой smoke (uvicorn + curl):
register 201, login 200 (`access_token`, `refresh_token`), `GET /v1/games`
с токеном 200 `[]`, без токена 401 `unauthorized`,
`POST /v1/analyze` без токена 401. Фронтенд: 36 тестов, `tsc --noEmit`
exit 0, `vite build` 99 модулей.

**Остаток.** Ограничения вынесены в KI-036 (пин bcrypt), KI-037 (нет
отзыва refresh/2FA/email-верификации; токены в `localStorage`), KI-038
(бюджеты токенов пока по IP). `/admin` по-прежнему использует отдельную
парольную сессию, а не JWT.

## KI-036 · Closed · Low · deps, auth

**Симптом.** `passlib` 1.7.4 несовместим с `bcrypt>=4.1` (модуль
`bcrypt.__about__` удалён): при первом хешировании passlib падает с
`ValueError: password cannot be longer than 72 bytes` в
`detect_wrap_bug`/`_load_backend_mixin`.

**Причина.** passlib давно не обновлялся и не поддерживает новую
версию bcrypt; bcrypt 5.0 также ужесточил проверку длины входа.

**Обход / текущее поведение.** В `pyproject.toml` зафиксирован
`bcrypt>=4.0,<4.1` (см. комментарий рядом с `passlib[bcrypt]`);
`app/auth/passwords.py` дополнительно проверяет 72-байтный лимит до
вызова passlib.

**План закрытия.** Перейти на поддерживаемую связку: `pwdlib[argon2]`
или `argon2-cffi` (DESIGN_ADMIN_AND_OPS §4.1 предполагает Argon2id;
постановка итерации 24 требовала passlib+bcrypt). После перехода —
миграция существующих bcrypt-хешей при первом успешном входе.

**Закрыт в итерации 26.** `passlib` и `types-passlib` удалены из
`pyproject.toml`; пароли — Argon2id (`argon2-cffi`, `$argon2id$…`).
`verify_and_update` проверяет legacy `$2b$`-хеши через `bcrypt.checkpw` и
возвращает новый Argon2id-хеш, `/auth/login` перезаписывает
`users.password_hash` в той же транзакции + лог `password_rehashed`.
bcrypt остаётся зависимостью только для этой миграции — KI-042, после
конвертации всех хешей её можно удалить. Тесты: argon2-roundtrip,
rehash-параметров, bcrypt→argon2 на живом логине, 8..256 символов.

## KI-037 · Closed · Med · auth, security

**Симптом.** JWT-аутентификация есть, но у неё нет управляемого
жизненного цикла: refresh-токены не отзываются (jti не хранится),
смены пароля/выхода «на всех устройствах» нет; access/refresh лежат в
`localStorage` (риск XSS-кражи); нет верификации email и сброса
пароля; отдельного лимита попыток входа по email нет (только общий
IP-rate-limit 10/мин на `/auth/login`).

**Причина.** Итерация 24 закрывала уязвимость KI-035 (отсутствие
изоляции данных) минимальным JWT-слоем; token denylist, email-flow и
httpOnly-cookie — отдельный объём.

**Обход / текущее поведение.** Access живёт 15 минут, refresh — 7 дней;
logout только чистит клиентское хранилище. Пароли — bcrypt (см. KI-036).
`/admin` по-прежнему использует отдельную парольную сессию
(`ADMIN_PASSWORD`), а не JWT.

**План закрытия.** Таблица `refresh_tokens`/`jti` denylist в Redis,
`POST /auth/logout`, ротация refresh с обнаружением повторного
использования; httpOnly+Secure cookie либо BFF; лимит попыток по
(email, IP); верификация email и сброс пароля; SSO — T-118.

**Закрыт в итерации 26 (в объёме cookie/denylist).** Refresh-токен больше
не возвращается в JSON: `/auth/login` и `/auth/refresh` кладут его в
HttpOnly-cookie (`SameSite=Lax`, `Path=/auth`, `Secure` при
`AUTH_COOKIE_SECURE=true`, `Max-Age` = TTL refresh); access живёт в памяти
фронтенда, `localStorage` для токенов не используется, все fetch идут с
`credentials: "include"`, на 401 — single-flight refresh по cookie.
Добавлен `POST /auth/logout`: `jti` refresh уходит в Redis
`refresh_denylist:<jti>` (TTL до `exp`), cookie очищается, повторное
использование отозванного токена → 401. Ротация refresh теперь также
отзывает предыдущий `jti` (защита от replay). Denylist fail-open при
недоступном Redis — осознанно и задокументировано. Остаток (2FA, email-
верификация, сброс пароля, отзыв всех сессий) — KI-041.

## KI-038 · Closed · Med · finops, auth

**Симптом.** После внедрения JWT лимиты токенов всё ещё считаются по
IP: `TokenBudgetMiddleware` и `request_subject`/`request_tier` в
`app/finops.py` не смотрят на пользователя; `/v1/users/me/usage`
показывает лимит по роли, а списывается бюджет по IP. Пользователь за
NAT/общим IP делит лимит с другими; админ/аудитор получает «pro» только
в ответе usage.

**Причина.** FinOps-слой (T-031) проектировался до JWT (KI-031):
`X-User-Tier`/`PRO_IPS` — временная замена ролей.

**Обход / текущее поведение.** Дневные лимиты free/pro по-прежнему
работают, но на IP-субъект. В тестах бюджет отключён
(`TOKEN_BUDGET_ENABLED=false`).

**План закрытия.** T-031b/T-041: брать `sub`/`role` из проверенного JWT в
middleware (или из `request.state.user`), субъект `user:<id>`, tier из
роли; durable-агрегаты `usage_daily` и месячные бюджеты по
пользователю/организации.

**Закрыт в итерации 26.** `app/finops.py` получил общий JWT-aware
резолвер: при валидном access-токене (подпись/exp, без запроса в БД)
субъект — `user:{id}`, tier из claim `role` (`admin`/`auditor` → `pro`,
`user` → `free`); анонимно/битый токен — прежний IP + `PRO_IPS`
(KI-031). `TokenBudgetMiddleware` и `/v1/users/me/usage` используют один
резолвер, ключ Redis — `usage:<date>:user:<id>`; интеграционные тесты
проверяют изоляцию A/B с одного IP и реальный `used` в usage-endpoint.
Остаток: tier берётся из claim на момент выдачи токена (смена роли — после
refresh до 15 мин), durable-агрегаты — T-031b (KI-043 не связан).

## KI-039 · Closed · Med · llm, dataset

**Симптом.** SFT-пара из `edits` учит модель **переписывать** уже готовый
комментарий: `scripts/export_dataset.py` кладёт в `user` исходный ответ
модели (`edits.original_text`), а в `assistant` — принятую правку
(`edits.edited_text`). На инференсе же модель получает «пакет фактов», а
не черновик, поэтому целевая задача обучения не совпадает с целевой

«оригинал → правка»; «пакет фактов», из которого сгенерирован
`original_text`, в датасет не попадает. Схема JSONL `schema_version=1`
(T-104, итерация 25) сохранила обратную совместимость с выгрузкой
итерации 19.

**Обход / текущее поведение.** Датасет валиден, обучение запускается, но
полученный адаптер (если его обучить на текущей схеме) — «редактор
комментариев», а не генератор из фактов. Оценка качества на инференсе
через `evaluate_llm.py` покажет, есть ли перенос.

**План закрытия.** До первого GPU-прогона решить один из вариантов:
(1) `schema_version=2`: в `user` — пакет фактов (`build_fact_package`),
в `assistant` — принятый комментарий (нужно сохранять пакет фактов при
генерации, миграция `commentaries`/`edits`); (2) принять
rewrite-постановку и подавать на инференсе «черновик модели + правка»;
(3) гибрид: отдельные adapter/промпт для rewrite-режима. После решения —
обучить на GPU (RunPod/Colab), прогнать `evaluate_llm.py` на 10–20
партиях и сравнить с baseline 4.40/10.

**Закрыт в итерации 26.** Выбран вариант (1): `scripts/export_dataset.py`
по умолчанию пишет `schema_version=2` — `system` (промпт уровня),
`user` = `build_fact_package(parse_pgn(game.pgn), load_analyses(...),
level)` (пакет фактов восстанавливается из `games`/`moves`/`motifs`),
`assistant` = `edited_text`; во вложенном `metadata` — id/commentary_id/
game_id/editor_id/level/model/created_at/fact_sheet_chars. Проблемные
записи (нет партии, битый PGN, нет анализа) пропускаются со статистикой.
`--schema-version 1` оставлен для сравнения (rewrite-семантика). 
`scripts/train_lora.py` поддерживает `{1,2}`, печатает распределение по
версиям, предупреждает о v1 и проверяет эвристику пакета фактов для v2.
`LORA_TRAINING.md` переписан под v2. Тесты: unit + интеграционный
seed→export→валидация. Обучение на GPU тогда не выполнялось (на тот момент
KI-030 был Open; 3B/7B-адаптеры обучены и отклонены в итерации 48).

## KI-041 · Closed · Low · auth, security

**Симптом.** В итерации 26 закрыт основной объём KI-037 (HttpOnly-cookie,
denylist, logout, отзыв при ротации), но управление жизненным циклом
аккаунта осталось неполным: нет 2FA, верификации email, сброса пароля,
«выйти на всех устройствах», отдельного лимита попыток по email; парольная
форма `/admin` — legacy fallback с единым `ADMIN_PASSWORD`, не БД-паролем.

**Причина.** Итерация 26 закрывала техдолг KI-036…039 в объёме DoD
(куки, denylist, роли в admin); email-flow/2FA/SSO — отдельный объём.

**Решение (итерация 32).**
- Миграция `dcf1da1421cd`: `users.is_verified` (`server_default=true` —
  legacy/админские учётки не теряют доступ; регистрация пишет `false`).
- `app/email/sender.py`: `EmailSender` Protocol + `MockEmailSender`
  (outbox + structlog-ссылка); SMTP — отдельная реализация.
- `POST /auth/register` → письмо `email_verify`; `GET /auth/verify-email`
  → `is_verified=true`; `/v1/analyze` и `/v1/commentary` для
  неподтверждённых → 403 `email_not_verified` (admin/auditor — bypass).

  `POST /auth/reset-password`: Argon2id-хеш, одноразовый токен, глобальный
  отзыв refresh.
- `POST /auth/logout-all`: Redis `revoked_before:<user_id>` (Unix-ms);
  `/auth/refresh` сравнивает `iat_ms`/`issued_at` и отвечает 401 для всех
  токенов, выпущенных до отзыва.
- Тесты: `tests/integration/test_auth_ki041.py` (8),
  `tests/unit/test_email_sender.py` (5), юнит-тесты global revocation в
  `tests/unit/test_auth.py`.

**Остаток.** Frontend-страницы verify/reset и logout-all закрыты в
итерации 33 (KI-055); 2FA/TOTP, SSO, лимит попыток по (email, IP),
реальный SMTP-провайдер и resend-verification — KI-056. Смена пароля
не отзывает уже выданные access-токены (живут до 15 мин) — стандартное
поведение JWT. Legacy-форма `/admin` с `ADMIN_PASSWORD` остаётся.

## KI-042 · Open · Low · deps, auth

**Симптом.** `bcrypt>=4.1` остаётся в зависимостях проекта, хотя новые
пароли хешируются Argon2id: bcrypt нужен только для проверки legacy
`$2a$`/`$2b$`/`$2y$`-хешей. Пока в БД есть хотя бы один bcrypt-хеш,
удаление зависимости сломает вход такого пользователя.

**Причина.** Миграция «на лету» при успешном логине: нет способа
перехешировать пароль пользователя, который не заходит.

**Обход / текущее поведение.** `verify_and_update` при bcrypt-хеше
возвращает Argon2id-хеш, `/auth/login` сохраняет его; событие
`password_rehashed` в structlog позволяет отслеживать прогресс. После
одноразовой миграции (скрипт с доступом к паролям невозможен) или
принудительного сброса паролей зависимость `bcrypt` удаляется.

**План закрытия.** Метрика/запрос «сколько `password_hash` начинается с
`$2`», период наблюдения; после нуля — удалить bcrypt из
`pyproject.toml` и ветку `_verify_bcrypt`. Тест: хеш-пароли в БД
покрываются миграцией.

## KI-043 · Closed · Low · auth, security

**Симптом.** User-enumeration по времени ответа: для несуществующего
email `/auth/login` отвечает 401 почти мгновенно, для существующего
выполняется Argon2id (~десятки миллисекунд). По разнице можно определить,
зарегистрирован ли email.

**Причина.** `verify_and_update` вызывается только когда пользователь
найден; для отсутствующего — ранний `raise AuthError`.

**Обход / текущее поведение.** Сообщение об ошибке одинаковое
(«Неверный email или пароль»), rate limit 10/мин на `/auth/login|register`
снижает скорость перебора. Практическая эксплуатация ограничена.

**План закрытия.** При отсутствии пользователя выполнять проверку
фиктивного Argon2id-хеша (dummy verify) и возвращать тот же 401;
нормализовать тайминг на тесте с допуском. Опционально — общий лимит
попыток по (email, IP) — см. KI-041.

**Закрыт в итерации 27.** В `app/auth/passwords.py` добавлен
`DUMMY_PASSWORD_HASH` (Argon2id с параметрами `PasswordHasher()` по
умолчанию); `/auth/login` при ненайденном email выполняет
`asyncio.to_thread(verify_password, password, DUMMY_PASSWORD_HASH)` перед
тем же 401. Тесты: unit (dummy вызывается ровно с DUMMY_HASH) и
интеграционный тайминг (7+7 запросов, медианы **55.4 мс** для
существующего и **54.8 мс** для несуществующего, ratio 1.01 при пороге
≤2.0 и обе >5 мс). KI-041 (лимит попыток по email) остаётся.

**Обход / текущее поведение.** Ограничение описано в LORA_TRAINING.md;

**План закрытия.** LRU/dict-кэш на время экспорта по `game_id`

## KI-046 · Closed · Low · observability, llm

## KI-047 · Closed · Low · observability

**Симптом.** Необработанные исключения (не `AppError`) в эндпоинте дают
500 **без** заголовка `X-Trace-Id`: в Starlette `ServerErrorMiddleware`
стоит снаружи пользовательских middleware, поэтому заголовок, который
добавляет `TraceMiddleware`, до такого ответа не доходит. Обработанные
ответы (404/422/429/доменные 4xx/5xx) заголовок имеют.

**Причина.** `X-Trace-Id` добавляется в `http.response.start` внутри
`TraceMiddleware`; `ServerErrorMiddleware` формирует собственный ответ
раньше.

**Решение (итерация 28).** App-level handler
`app.add_exception_handler(Exception, _unhandled_error_handler)`:
читает `request.state.trace_id` (его выставил TraceMiddleware до входа в
приложение), возвращает `500 {"detail": "Internal Server Error",
"code": "internal_error"}` с заголовком `X-Trace-Id`, пишет
`unhandled_exception` в structlog (path/method/trace_id/тип, без текста
исключения). `AppError` продолжает обрабатываться отдельным handler'ом.
Тест: `test_tracing.py::test_unhandled_500_has_trace_id_header`.

**Остаток.** Если исключение произошло до `TraceMiddleware` (например, в
самом первом middleware), `trace_id` может отсутствовать — тогда
заголовок не выставляется (handler не падает).

## KI-048 · Closed · Low · db, observability

**Симптом.** `llm_calls` (T-030) — обычная append-only таблица без
партиционирования/retention: при росте трафика она будет расти
неограниченно, нет 90-дневного удержания. Durable-агрегат `usage_daily`
добавлен в итерации 28 (T-031b), но партиций/retention для `llm_calls`
по-прежнему нет. Индексы BRIN/DESC уже есть, что сглаживает чтение

**Причина.** Для MVP осознанно выбрана непартиционированная таблица:
партиционирование требует изменения ключа уникальности
(`trace_id, span_id, created_at`) и фоновой ротации.

**Решение (итерация 29).** `scripts/prune_llm_calls.py` удаляет строки
старше `LLM_CALLS_RETENTION_DAYS` (90 по умолчанию) **батчами**:
`DELETE FROM llm_calls WHERE id IN (SELECT id ... ORDER BY id LIMIT N)` в
цикле, commit на батч, пауза `--sleep-ms` между батчами; `--dry-run`,
`--max-batches`, `--json`, exit code 0/2. Запуск — cron/планировщик
(`GETTING_STARTED.md` §9.1). Тесты:
`tests/unit/test_prune_llm_calls.py`,
`tests/integration/test_prune_llm_calls.py`.

**Остаток.** Партиционирование по месяцу не сделано — вынесено в KI-052:
оно потребует сменить `UNIQUE (trace_id, span_id)` на
`(trace_id, span_id, created_at)` и пересоздать таблицу; для MVP
батчевого retention достаточно.

## KI-049 · Open · Low · finops, db

**Симптом.** Durable-агрегат `usage_daily` пишется из
`record_token_usage` в фоне (`asyncio.create_task`). Если процесс упадёт
между Redis-`INCRBY` и INSERT/COMMIT, дельта расхода не попадёт в БД;
после рестарта Redis-ключ потеряется, и `/v1/users/me/usage` покажет

вниз»; потеря возможна только для последней дельты при жёстком падении.

**План закрытия.** Outbox/очередь (Redis Stream/ARQ): сначала durable
INSERT, затем Redis-инкремент (или at-least-once ретраи); cron/Temporal
для `aggregate_usage.py` и алертов 80/100% (T-031b остаток).

## KI-052 · Open · Low · db, observability

**Симптом.** `llm_calls` не партиционирована по месяцам: таблица остаётся
одним append-only отношением, а единственный механизм удержания —

отдельно (в постановке итерации 29 оно было опциональным).

**Обход / текущее поведение.** Ежедневный `prune_llm_calls.py` держит
таблицу в пределах 90 дней; BRIN-индекс по `created_at` ускоряет
диапазонные чтения. Размер таблицы на dev/тестовых прогонах мал.

**План закрытия.** Отдельная миграция: новая партиционированная таблица
`llm_calls` (RANGE по `created_at`, помесячно), перенос данных, смена
уникального ключа на `(trace_id, span_id, created_at)`, автоматическое
создание партиций (pg_partman или cron-миграция на месяц вперёд),
адаптация `app.llm.calls` и тестов миграции.

## KI-060 · Open (частично исправлен) · Med · llm, training, dataset

**Симптом.** LoRA-адаптер `qwen-7b-tokenizer` (Qwen2.5-7B) в комментарии

зафиксировал китайские слова/иероглифы в одном из 5 комментариев
(итерация 48). Средняя оценка 7B — **3.33/10** против **4.40/10** у
zero-shot Qwen3-4B; помимо дрейфа языка судья отмечает выдуманные лучшие
ходы и путаницу сторон. Отчёт — `docs/development/reports/LLM_EVAL.md`,

момент итерации 48 — файл перезаписан прогонами v2/v3).

**Причина.** Переобучение на узком и шумном golden-датасете: ~1000
примеров, сгенерированных той же 4B-моделью, 3 эпохи QLoRA. Базовая
Qwen2.5-7B мультиязычна и «китаецентрична»; при малом объёме
русскоязычных SFT-пар и высокой LR распределение языка сдвигается к
китайскому. Промпт требует русский текст, но валидатор проверяет только
легальность SAN, а не язык/алфавит, поэтому дрейф не отсекается.

**Обход / текущее поведение.** 7B-адаптер в продакшене **не
используется**: остаётся базовая 4B (Qwen3-4B). 3B-адаптер также

**Остаток (обновлено в итерации 53).**

  cache-hit без CJK-фильтра — отдельный остаток KI-060.
* **Диапазон детектора** — только CJK Unified Ideographs (U+4E00–U+9FFF):
