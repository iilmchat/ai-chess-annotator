## 1. Принципы

- **Факты — от движка, текст — от LLM.** Любой шахматный вариант,
  упомянутый в комментарии, должен быть проверен Stockfish через модуль
  `validator`. Исключений нет.
- **Уровень — это политика, а не только промпт.** Рекомендуемый ход
  выбирается детерминированной функцией `policy(recommended_for_level)`, а
  LLM уже облекает его в текст.
- **Источник истины — один.** Архитектурные решения — только в `SPEC.md`.
  Дублирование факта в нескольких документах запрещено; вместо этого —
  ссылка.
- **Не перескакивать через зависимости.** В `TODO.md` у каждой задачи
  указано `Зависит от:`. Если зависимость не закрыта — задача не
  начинается.
- **Блокер — это нормально.** Лучше завести `KI-NNN` и остановиться, чем
  обойти проблему «временным решением», которое потом забывается.
- **Маленькие итерации.** Одна итерация — одна группа задач из `TODO.md`.
  В конце итерации — зелёный CI и отчёт в `RELEASES.md`.

## 2. Ветвление и коммиты

### 2.1. Ветки

- `main` — всегда зелёная, всегда готова к деплою.
- `iter/NN-<slug>` — рабочая ветка итерации. Пример:
  `iter/01-bootstrap`, `iter/07-ingestion`.
- `fix/KI-NNN-<slug>` — исправление известной проблемы. Пример:
  `fix/KI-012-healthcheck-redis-timeout`.
- `exp/<slug>` — эксперименты, не идущие в `main` напрямую.

Мерж в `main` — только через PR с зелёным CI и ревью (человек или DSH-ревьюер
по чек-листу §10).

### 2.2. Сообщения коммитов — Conventional Commits

```
<type>(<scope>): <subject>

[optional body]

[optional footer: Refs: T-NNN, KI-NNN]
```

**Типы:** `feat`, `fix`, `chore`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`.

**Scope** — модуль или задача: `ingestion`, `engine`, `db`, `api`, `web`,
`docs`, `ci`. Допускается `T-007` вместо scope, если задача крупная.

**Примеры:**

```
feat(ingestion): parse PGN and detect ECO code (T-007)
fix(engine): handle Stockfish process restart on crash (KI-014)
docs(rules): add commit message conventions
test(api): cover /v1/analyze with 5 PGN fixtures (T-009)
```

**Запрещено:**
- Коммитить с `--no-verify` (Husky-хуки обязательны).
- Коммитить секреты (`.env`, ключи, токены). Husky блокирует паттерны
  реальных ключей.
- Смешивать в одном коммите несвязанные изменения (например, фикс бага +
  рефакторинг + новую фичу). Дели на атомарные коммиты.

### 2.3. PR

- Название PR = `<type>(<scope>): <краткое описание> (T-NNN..T-MMM)`.
- В описании — ссылки на задачи из `TODO.md` и отчёт итерации из
  `RELEASES.md`.
- CI должен быть зелёным. Красный CI — PR не мержится, даже если «почти
  работает».
- Ревьюер проверяет чек-лист §10.

## 3. Код

### 3.1. Backend (Python 3.12)

- **Стиль:** `ruff` с конфигом из `pyproject.toml` (`line-length = 100`,
  `target-version = "py312"`). Нарушения — блокер для мержа.
- **Типы:** `mypy --strict` обязателен. Публичные функции и методы — с
  аннотациями. `Any` — только с `# type: ignore[...]` и комментарием,
  почему.
- **Async:** весь I/O — `async`/`await`. Синхронные блокирующие вызовы
  (например, `subprocess` для Stockfish) — только через
  `asyncio.to_thread` / `run_in_executor`.
- **Pydantic v2:** все входы/выходы API — через `BaseModel`. Никаких
  «голых» `dict` в публичных сигнатурах.
- **SQLAlchemy 2.0:** `Mapped[...]`, `mapped_column`. Никаких старых
  `declarative_base()` и `Column(...)`.
- **Alembic:** одна миграция — одно логическое изменение. Автогенерация —
  только с ревью; ручные правки миграций допустимы, если autogenerate не
  видит индекс/enum.
- **Логи:** `structlog`, structured JSON. Никаких `print()`. Уровни:
  `debug` — для отладки, `info` — для бизнес-событий, `warning` — для
  восстановимых проблем, `error` — для сбоев, требующих внимания.
- **Ошибки:** собственные исключения в `app/errors.py`. `HTTPException`
  только на уровне API. Никаких «голых» `raise Exception("...")`.
- **Конфиг:** только через `Settings` (pydantic-settings). Чтение
  `os.environ` напрямую — запрещено.

### 3.2. Frontend (React 19 + TypeScript)

- **Стиль:** `tsc --noEmit` обязателен, `strict: true`. `any` — только с
  `// eslint-disable-next-line` и комментарием.
- **Компоненты:** функциональные, без классов. Хуки — по правилам React.
- **Состояние:** Zustand для глобального, `useState` для локального. Никаких
  Redux/MobX без согласования.
- **Запросы:** `fetch` обёрнут в `lib/api.ts` с типами. Ответы
  валидируются Zod-схемами (когда появится Zod — задача T-019+).
- **Стили:** Tailwind CSS 4. Никаких inline-стилей, кроме одноразовых
  экспериментов (которые не мержатся).
- **i18n:** все строки — через `react-i18next`. Хардкод строк в JSX —
  запрещён.
- **Производительность:** route-level code-split для страниц. Основной
  чанк — ≤ 200 kB (gzip).

### 3.3. Общее

- **Не менять стек** без явного согласования (Python 3.12, FastAPI, React 19,
  PostgreSQL 17 + pgvector, Redis, Stockfish 17, vLLM).
- **Не добавлять зависимости** без обоснования в PR. Каждая новая
  зависимость — с указанием, зачем и почему нельзя обойтись стандартной
  библиотекой.
- **Не коммитить сгенерированные файлы** (`web/dist/`, `alembic/versions/*.pyc`,
  `node_modules/`, `__pycache__/`).
- **Не коммитить локальные данные** (`data/`, `.env`, `.venv/`).

## 4. Тесты

### 4.1. Обязательный минимум

- **Каждая новая функция/метод** — с unit-тестом. Если функция тривиальна
  (getter/setter) — тест можно не писать, но это надо явно указать в PR.
- **Каждый эндпоинт API** — с интеграционным тестом (FastAPI TestClient).
- **Каждая миграция** — тест на `upgrade` + `downgrade` + повторный
  `upgrade`.
- **Каждый промпт** — тест на «пакет фактов → промпт содержит все
  обязательные поля».
- **Каждый валидатор** — тест на все классы ошибок (нелегальный ход,
  зевок в варианте, отсутствующий вариант).

### 4.2. Пирамида

- **Unit** — 70%: чистая логика, без БД и сети.
- **Integration** — 25%: API + БД (testcontainers / docker compose),
  движок (реальный Stockfish на малой глубине).
- **E2E** — 5%: Playwright на фронтенде + полный сценарий PGN → комментарий.

### 4.3. Структура

```
tests/
├── unit/
│   ├── test_ingestion.py
│   ├── test_engine.py
│   ├── test_policy.py
│   ├── test_validator.py
│   └── ...
├── integration/
│   ├── test_api_analyze.py
│   ├── test_api_commentary.py
│   └── ...
├── e2e/
│   └── test_full_flow.py
└── fixtures/
    ├── example.pgn
    ├── annotated_games/*.pgn
    └── ...
```

### 4.4. Правила

- **Тесты не должны зависеть от порядка выполнения.** Каждый тест —
  изолирован.
- **Тесты не должны ходить в интернет.** Внешние LLM — через моки. Stockfish
  — реальный, но на малой глубине (`depth=10`), либо через мок UCI-канала.
- **Тесты не должны разделять состояние** (БД, Redis, файлы). Каждый
  integration-тест — в транзакции с rollback, либо на отдельной БД.
- **Flaky-тесты — блокер.** Если тест иногда падает — заведи `KI-NNN`,
  опиши условия, и либо почини, либо временно пометь `@pytest.mark.skip` с
  комментарием и `KI-NNN`.
- **Покрытие:** целевое ≥ 80% для `app/`, ≥ 60% для `web/src/`. Цифры —
  ориентир, не догма: важнее критичные пути (ingestion, engine, validator,
  policy).

## 5. Документация

### 5.1. Что и где

- **`SPEC.md`** — единственный источник истины по архитектуре, схеме БД,
  API, промптам, критериям приёмки. Любое изменение архитектуры — сначала
  в `SPEC.md`, потом в коде.
- **`ARCHITECTURE.md`** — «как это устроено сейчас»: диаграммы модулей,
  потоки данных, контракты между сервисами. Ссылается на `SPEC.md`.
- **`GETTING_STARTED.md`** — «как развернуть за 20 минут». Обновляется при
  изменении способа запуска.
- **`USER_GUIDE.md`** — «как пользоваться». Обновляется при каждой новой
  фиче, видимой пользователю.
- **`RULES.md`** — этот документ.
- **`PROMPT_CURRENT.md`** — актуальные системные инструкции для DSH и
  метрики. Обновляется при изменении правил.
- **`RELEASES.md`** — журнал итераций. Заполняется в конце каждой
  итерации.
- **`CHANGELOG.md`** — по [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/).
  Каждая новая фича/фикс — строка.
- **`KNOWN_ISSUES.md`** — реестр проблем. Формат: `KI-NNN · статус ·
  severity · модули · план закрытия`.
- **`docs/development/vX.Y/DESIGN_VXY.md`** — дизайн-документ итерации.
  Пишется **до** кода, если итерация меняет архитектуру.

### 5.2. Правила

- **Один факт — один источник.** Дублирование запрещено. Ссылки вместо
  копий.
- **Каждый PR** обновляет затронутые документы. PR без обновления
  документации (если код меняет поведение) — не мержится.
- **Язык:** документация — на русском (для внутренней команды). Публичные
  README и USER_GUIDE — на русском + английском (по мере готовности
  локализации).
- **Формат:** markdown, GFM-совместимый. Оглавление — для документов
  длиннее 3 разделов. Якоря — для навигации.

## 6. Итерации и отчёты

### 6.1. Планирование

- Итерация = одна группа задач из `TODO.md` (одна фаза, либо явно
  выделенная подгруппа).
- В начале итерации — короткий план в `RELEASES.md`: какие задачи, в каком
  порядке, какие риски.
- Если задача оказалась больше, чем думали — **разбей её** на подзадачи
  (`T-NNNa`, `T-NNNb`) и обнови зависимости в `TODO.md`. Не растягивай
  итерацию.

### 6.2. Выполнение

- Работай по шагам, после каждого — проверяй результат (`ruff`, `mypy`,
  `pytest`, `pnpm typecheck`, `curl`).
- Каждый шаг — отдельный коммит (или несколько атомарных). Не копи
  изменения до конца итерации.
- Блокер — сразу `KI-NNN` и стоп. Не пытайся обойти.

### 6.3. Завершение итерации

Итерация завершена, когда:

1. Все задачи из группы закрыты (`[x]` в `TODO.md`), **или** явно
   перенесены в `KNOWN_ISSUES.md` с `[~]` и `KI-NNN`.
2. `ruff check .`, `mypy app`, `pytest -q` — зелёные.
3. `pnpm --dir web typecheck && pnpm --dir web build` — зелёные (если
   трогали фронтенд).
4. CI на ветке `iter/NN-*` — зелёный.
5. Отчёт в `RELEASES.md` заполнен:
   - что сделано (список задач);
   - что не сделано и почему (ссылки на KI);
   - метрики: тесты, CI, ключевые бенчмарки;
   - что дальше.
6. `CHANGELOG.md` обновлён (секция `[Unreleased]`).
7. README обновлён (статус, счётчики тестов).
8. PR в `main` создан и смержен.

## 7. Безопасность

### 7.1. Секреты

- **Никогда** не коммитить `.env`, ключи API, пароли, токены.
- Все секреты — в ENV (dev) или Vault/SOPS (prod).
- `.env.example` содержит только placeholder'ы (`change_me_*`,
  `your_api_key_here`).
- Husky блокирует коммиты с паттернами реальных ключей (OpenAI, Anthropic,
  DeepSeek, AWS и т.д.). Не обходить через `--no-verify`.
- Ключи провайдеров шифруются AES-256-GCM перед сохранением в БД.

### 7.2. Аутентификация и авторизация

- JWT + refresh-токены. Access-токен — 15 минут, refresh — 7 дней.
- Роли: `owner`, `editor`, `viewer`. Проверки — на уровне эндпоинта, не
  только на фронтенде.
- Rate limiting через Redis: 5 запросов/мин на login, 300/мин общий лимит.

### 7.3. Приватность партий

- Партии пользователей **не уходят** во внешние LLM при уровне «новичок»
  (локальная модель) и при явном `privacy=local` (любой уровень).
- Для уровня «гроссмейстер» — опция «только локально» (`LLM_PROVIDER=local`).
- При отправке во внешнюю LLM — только «пакет фактов» без PGN-метаданных
  (имена игроков, event, дата) и без user_id.
- GDPR: право на удаление (эндпоинт `DELETE /v1/users/me`), экспорт
  (`GET /v1/users/me/export`).

### 7.4. Валидация входных данных

- Все входы — через Pydantic-схемы с `strict=True` где возможно.
- PGN/FEN — валидируются через `python-chess`; невалидный ввод → 400.
- Загружаемые файлы (PGN, аннотированные партии) — лимит размера
  (10 MB для PGN, 5 MB для аннотаций), проверка MIME, защита от
  ZIP-бомб (для будущих форматов).
- SSRF-защита: единый `SafeHttpClient` для любых исходящих HTTP-запросов
  (проверка всех DNS-адресов, защита от DNS rebinding, ручная
  перепроверка редиректов).

## 8. Работа с LLM и движком

### 8.1. LLM

- **Все варианты — только из «пакета фактов».** LLM не имеет права
  «придумывать» ходы. Промпт содержит `ЗАПРЕЩЕНО выдумывать варианты.
  Используй только факты из пакета`.
- **Валидатор обязателен.** Каждый вариант из LLM-ответа прогоняется через
  Stockfish. Нелегальный/ошибочный → retry LLM с уточнением. Если после
  N retry (default 2) вариант всё ещё невалиден — он вырезается из
  ответа, в логи пишется `warning`, в `KNOWN_ISSUES.md` — `KI-NNN`, если
  проблема системная.
- **Промпты версионируются.** `app/prompts/<level>.txt` — файлы, не
  строки в коде. Изменение промпта — отдельный PR с тестом на «пакет
  фактов → промпт содержит все обязательные поля» и ручной проверкой
  на 5 тестовых партиях.
- **Стоимость контролируется.** У каждой LLM-модели — лимит
  `max_tokens` и `cost_cap` на запрос. Превышение — ошибка, не «тихое»
  списание.
- **Fallback.** Если локальная LLM недоступна — fallback на облачную
  (если разрешено настройками приватности). Если облачная недоступна —
  ошибка `503` с понятным сообщением.

### 8.2. Движок

- **Stockfish — через UCI.** Один процесс на воркер (или пул процессов).
  Таймауты обязательны (`movetime` + `timeout` на чтение UCI-потока).
- **Глубина по уровню** — из `SPEC.md` §2.2. Не менять без согласования:
  это влияет на латентность и стоимость.
- **Бенчмарки.** Для каждой итерации, затрагивающей движок, — бенчмарк
  латентности на тестовой партии (40 ходов, уровень «клуб»). Цель:
  ≤ 30 сек на партию (из `SPEC.md` §9).
- **Leela Chess Zero** — опционально, только для уровня «гроссмейстер».
  Подключается как второй движок (T-101). Пока не реализовано — не
  упоминать в промптах как «доступное».

## 9. Обработка блокеров

### 9.1. Что считается блокером

- Шаг из `TODO.md` не выполняется из-за внешней причины (Docker, сеть,
  отсутствие ключа, конфликт версий).
- Тест падает нестабильно (flaky).
- Обнаружено противоречие в `SPEC.md` или `TODO.md`.
- Обнаружена уязвимость или утечка секрета.

### 9.2. Что делать

1. **Завести `KI-NNN`** в `docs/KNOWN_ISSUES.md`:
   - `KI-NNN · Open · <severity> · <модули> · <план закрытия>`.
   - Описание: что делал, что ожидал, что получил, окружение.
   - Если возможно — ссылка на issue в GitHub.
2. **Пометить задачу** в `TODO.md` как `[~]` со ссылкой на `KI-NNN`.
3. **Остановиться.** Не перескакивать через зависимость. Не обходить
   «временным решением» без записи в `KNOWN_ISSUES.md`.
4. **Сообщить** в чат: `⚠️ шаг N — блокер: <описание>, KI-NNN`.
5. **Ждать решения** (или предложить варианты в чате).

### 9.3. Severity

- **Critical** — блокирует весь проект (нет доступа к БД, нет Stockfish,
  утечка секрета).
- **High** — блокирует текущую итерацию (падает CI, не работает ключевой
  эндпоинт).
- **Med** — блокирует одну задачу (нестабильный тест, отсутствует
  опциональная зависимость).
- **Low** — не блокирует, но стоит починить (опечатка в документации,
  неоптимальный запрос).

## 11. Окружение и воспроизводимость

Правила ниже — не пожелания, а выводы из конкретных падений итерации 1
(см. `docs/development/reports/iteration-1/`).

### 11.1. Адреса: `127.0.0.1`, а не `localhost`

На Windows `localhost` резолвится сначала в `::1`, а `docker compose`
публикует порты только на IPv4-loopback (`127.0.0.1`). redis-py, в
отличие от asyncpg, не перебирает адреса и падает с
`TimeoutError: Timeout connecting to server` (STEP-06). Поэтому:

- `POSTGRES_HOST=127.0.0.1`, `REDIS_URL=redis://127.0.0.1:<port>/0` — в
  `.env`, `.env.example`, `app/config.py` и в CI;
- в `docker-compose.yml` порты публикуются как
  `"127.0.0.1:${PORT:-default}:<container>"`, наружу (`0.0.0.0`) — никогда.

### 11.2. Порты и конфликты с чужими контейнерами

- Канон: Postgres `5434`, Redis `6380`, API `8000`.
- Redis переопределяется `REDIS_PORT`; если порт занят другим проектом —
  не убивать чужой контейнер, не публиковать в обход: задать свободный
  порт через ENV, завести `KI-NNN` и записать фактический порт в отчёт
  (так появились KI-001 и KI-002).
- `.env` — локальный, в git не попадает; `.env.example` хранит канон.

### 11.3. Stockfish

- Бинарник в репозиторий не коммитится (79 МБ). Ставится в CI
  (`apt-get install -y stockfish`), на Windows — вручную (см. KI-006).
- `STOCKFISH_PATH` — абсолютный путь; на Windows — ASCII-путь (не
  `%LOCALAPPDATA%` с кириллицей), чтобы не ловить проблемы с кодировкой в
  subprocess.
- Проверка healthcheck — только `shutil.which`; глубина/таймауты движка
  появятся в T-008.

### 11.4. Миграции с `VECTOR` и нативными enum

Ловушки, на которые уже наступали (STEP-04):

1. `import pgvector` в файле миграции — Alembic рендерит
   `pgvector.sqlalchemy.vector.VECTOR(dim=...)`, без импорта — `NameError`.
2. `op.execute("CREATE EXTENSION IF NOT EXISTS vector")` — **до**
   `create_table` с `VECTOR`. В `downgrade` расширение не удаляется
   (KI-003).
3. Нативный enum: `postgresql.ENUM(..., create_type=False)` в колонках +
   явные `create()/drop()`; иначе `downgrade base` оставляет тип и
   повторный `upgrade` падает на `type "level" already exists`.
4. После любой правки миграции:
   `alembic upgrade head`, `alembic check`,
   `alembic downgrade base && alembic upgrade head`.

### 11.5. pnpm 12

- Настройки pnpm 12 читаются из `pnpm-workspace.yaml`, а не из
  `package.json#pnpm` и не из `.npmrc`.
- postinstall чужой зависимости разрешается точечно:
  `allowBuilds: {esbuild: true}`. `dangerouslyAllowAllBuilds` в проекте
  запрещён (supply-chain).
- `web/pnpm-lock.yaml` коммитится; CI кэширует по нему.

### 11.6. Прочее, что уже стреляло

- **Имя `text`.** В `app/db/models.py` (колонка `commentaries.text`)
  модуль импортирует `from sqlalchemy import text as sql_text`, иначе
  `server_default=text("false")` типизируется как `Mapped[str]` и mypy
  падает.
- **`session.refresh()` в async.** Просрочивает связанные объекты →
  следующий синхронный доступ к атрибуту даёт `MissingGreenlet`. Читать
  значения defaults через `select(...)`.
- **Семантика healthcheck.** `skipped` (LLM не настроена) — это
  `degraded`, а не `ok`: «всё хорошо» только когда все компоненты `ok`.
- **`types-redis`.** Не добавлять: redis 5.x поставляет `py.typed`, а
  стабы 4.6 маскируют `aclose`/`from_url`. Если понадобится обход
  upstream-пробела — узкий `# type: ignore[no-untyped-call]` + KI (KI-004).

## 12. Отчёты по шагам итерации

Помимо итогового отчёта в `RELEASES.md`, каждый шаг итерации
документируется отдельным файлом:

```
docs/development/reports/iteration-N/STEP-MM_<ТЕМА>.md
```

Обязательные разделы:

1. **Шапка:** дата, итерация, задача (`T-NNN`), статус
   (`✅ / ⚠️ / ❌`).
2. **Что сделано** — пронумерованный список, без «воды».
3. **Проверки** — таблица «проверка → команда → результат», с фактическим
   выводом (не «работает», а `5 passed`, JSON, `exit=0`).
4. **Файлы** — что создано/изменено и зачем.
5. **Проблемы и отклонения** — со ссылками `KI-NNN`; если обошли —
   почему именно так, а не иначе.
6. **Обоснование решений** — варианты, что выбрали, последствия.
7. **Что дальше** — следующий шаг.

Шаг без отчёта считается незавершённым (как и шаг без зелёных проверок).
