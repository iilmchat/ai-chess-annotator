## 1. Сколько времени есть и сколько нужно

| Величина | Значение |
| :--- | :--- |
| SLA (SPEC §9) | `/v1/analyze` ≤ 30 с на партию из 40 ходов, уровень «клуб» |
| Стоимость одной позиции | ≈ 1004 мс (movetime 1000 мс, замер итерации 3) |
| Позиций на 53 полухода | 54 (`N + 1`: старт + после каждого хода) |
| Последовательно | ≈ 54 с; на 40 ходов (81 позиция) ≈ 81 с |
| Хост | Intel Xeon E5-2690 v3, 12 ядер / **24 потока** |

Вывод: один процесс физически не успевает. Нужно `N` независимых
процессов; при 4 пулах 54 позиции раскладываются на 14 «волн» по 1 с.

## 2. Почему пул процессов, а не «параллельные вызовы одного сервиса»

`EngineService` держит **один** UCI-процесс и сериализует запросы
`asyncio.Lock`. Параллельные `asyncio.gather` по одному сервису просто
встанут в очередь на локе — ускорения нет. UCI-сессия однопоточная по
природе: один `go` за раз, иначе ответы перемешаются.

`movetime` — это wall-clock бюджет **каждого** процесса, поэтому 4
процесса, каждый со своим 1 с, дают почти линейное ускорение (потоков
хватает: 4 × 1 поток на 24 логических).

## 3. Устройство `EnginePool`

```
                ┌────────────┐
 54 FEN ──────▶ │ asyncio.Queue (свободные сервисы) │
                └─────┬──────┘
     ┌────────────────┼────────────────┐
     ▼                ▼                ▼
 EngineService#1  EngineService#2  EngineService#3  EngineService#4
 (UCI-процесс)    (UCI-процесс)    (UCI-процесс)    (UCI-процесс)
```

* `size` берётся из `settings.engine_pool_size` (по умолчанию **4**,
  ограничение `MAX_POOL_SIZE = 8`);
* процессы стартуют лениво — при первом `analyze`, а не в конструкторе;
* `analyze_positions` создаёт задачу на каждую позицию; одновременно
  работают ровно `size` задач (остальные ждут в `Queue.get()`);
* результаты складываются **по индексу**, порядок сохраняется;
* ошибки собираются в список, после `gather` поднимается первая — при
  этом остальные задачи успевают завершиться и вернуть движки в пул;
* `aclose()` гасит все процессы параллельно.

## 4. Что пришлось вынести в общие функции

`analyze_game_moves` у `EngineService` и у `EnginePool` должны считать
дельты/классификацию одинаково. Чтобы не копировать 60 строк, из
`service.py` выделены:

* `prepare_positions(moves, initial_fen)` — восстанавливает доски и UCI
  сыгранных ходов, сверяет FEN-ы (ошибка истории → `InvalidPgnError`);
* `build_move_analyses(moves, boards, played_uci, lines_by_position, classify)`
  — считает `eval_before/after`, `delta_cp`, `best_move_san`,
  `classification`, `engine_depth`, `mate_after`.

Побочно в `MoveAnalysis` добавлены `engine_depth` и `mate_after` (нужны
для записи в БД: `moves.engine_depth`, `moves.eval_mate`).

## 5. Почему не TaskGroup

`asyncio.TaskGroup` отменяет «соседние» задачи при первой ошибке. Для UCI
это опасно: задача может быть отменена посреди `go`, и следующий `go` на
том же процессе прочитает хвост предыдущего поиска (рассинхрон
протокола). Поэтому используется `gather` с `return_exceptions=True`:
все поиски доводятся до `bestmove`, движки возвращаются в пул, и только
потом поднимается первая ошибка. Отмена по разрыву клиента всё равно
возможна — `_UciEngine` на `CancelledError` убивает процесс, а не
оставляет его в неизвестном состоянии.

## 6. Проверки

| Проверка | Результат |
| :--- | :--- |
| Параллелизм | fake-движок: 9 позиций, пул 3 → максимум 3 одновременных вызова |
| Порядок | результаты совпадают с порядком FEN-ов |
| Ошибка | `EngineError` из одной позиции → исключение из `analyze_positions` |
| `size` | из настроек; `> MAX_POOL_SIZE` обрезается; `0` → `ValueError` |
