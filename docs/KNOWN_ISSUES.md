# Known Issues — ChessAnnotator

Реестр известных проблем, ограничений и отклонений окружения.
Формат записи (`RULES.md` §9.2):

```
## KI-NNN · Open|Closed · Low|Med|High|Critical · <модули>
**Симптом.** …
**Причина.** …
**Обход / текущее поведение.** …
**План закрытия.** …
```

Правило: любое отклонение — здесь. «Замазать» молча (широкий `except`,
`--passWithNoTests`, отключённый линтер) запрещено: запись в реестр
обязательна.

## KI-001 · Open · Low · infra, dev-env

**Симптом.** `docker compose up -d postgres redis` падает:

```
Error response from daemon: ports are not available: exposing port TCP
127.0.0.1:6380 -> 127.0.0.1:0: listen tcp4 127.0.0.1:6380: bind: Only one
usage of each socket address (protocol/network address/port) is normally permitted.
```

**Причина.** На dev-машине `127.0.0.1:6380` уже опубликован контейнером
`ticket-redis` другого проекта (`0.0.0.0:6380->6379/tcp`).

**Обход / текущее поведение.** Порт Redis в `docker-compose.yml` —
`"127.0.0.1:${REDIS_PORT:-6380}:6379"`. Канон 6380 сохранён (CI, прод,
чистые машины), локально в `.env` задано `REDIS_PORT=6381` и
`REDIS_URL=redis://127.0.0.1:6381/0`. `docker compose ps` показывает
`6379/tcp` → `127.0.0.1:6381`, healthcheck `redis: ok`.

**План закрытия.** Не требует кода. При освобождении 6380 — убрать
`REDIS_PORT` из локального `.env`. В прод-стеке порт наружу не
публикуется вовсе.

## KI-002 · Open · Low · api, dev-env

**Симптом.** `uvicorn app.main:app --port 8000` не стартует: порт занят.

**Причина.** `127.0.0.1:8000` занят контейнером `ai-opencamera-api-1`
(другой проект, публикация через Docker Desktop).

**Обход / текущее поведение.** Живая проверка healthcheck выполнена на
`127.0.0.1:8010` (отчёт `reports/iteration-1/STEP-06_HEALTHCHECK.md`).
Ответ API от номера порта не зависит; Vite-прокси в `web/vite.config.ts`
по-прежнему указывает на `localhost:8000` — на этой машине для
фронтенд-разработки нужно либо освободить 8000, либо поправить прокси
локально.

**План закрытия.** Освободить 8000 (остановить чужой контейнер) либо
сделать порт API настраиваемым (`API_PORT` + переменная прокси в Vite) —
кандидат в T-019.

## KI-003 · Open · Low · db, migrations

**Симптом.** После `alembic downgrade base` расширение `vector` остаётся
установленным в БД.

**Причина.** `downgrade` миграции `b802598c3778` намеренно не делает
`DROP EXTENSION vector`: расширение — свойство базы, а не схемы; в
общей БД им могут пользоваться другие схемы, а `DROP EXTENSION ... CASCADE`
удалил бы чужие объекты.

**Обход / текущее поведение.** `downgrade base` возвращает только схему
`public` к состоянию «нет таблиц» (проверено), тип `level` удаляется.
Для полностью чистой БД — `docker compose down -v`.

**План закрытия.** Не планируется; при необходимости — отдельная
административная команда вне Alembic.

## KI-004 · Open · Low · api, typing

**Симптом.** `mypy app`:

```
app/api/v1/health.py: error: Call to untyped function "from_url" in typed context
```

**Причина.** `redis-py` 5.3 поставляет `py.typed`, но `Redis.from_url`
в inline-типах остаётся без аннотаций (upstream-пробел). Стабы
`types-redis` 4.6 не помогают: они описывают redis 4.x и не знают
`aclose`.

**Обход / текущее поведение.** В `app/api/v1/health.py` узкий
`# type: ignore[no-untyped-call]` с комментарием; `types-redis` удалён из
dev-зависимостей.

**План закрытия.** Убрать ignore, когда redis-py аннотирует `from_url`
(проверять при обновлении `redis`).

плановом обновлении зависимостей (не раньше Фазы 1).

**План закрытия.** Скрипт `scripts/install-stockfish.ps1` (Windows) +
раздел в `GETTING_STARTED.md`; кандидат в T-008 (Engine Service).

## KI-011 · Open · Med · ingestion

**Симптом.** `ParsedGame.eco_code` равен `None` для партий без заголовка
`[ECO]`, если ходы не попали в курируемую таблицу префиксов
(`app/ingestion/eco.py`, ~50 записей). Детект транспозиций ограничен
повторением одной и той же позиции внутри партии
(`find_position_repeats`); «транспозиция относительно теории» (другой
порядок ходов, приводящий к известной позиции дебюта) не работает.

**Причина.** `python-chess` не поставляет базу ECO: в нём нет ни
каталога ECO, ни opening book. Полная классификация требует внешних
данных (полиглот-книга `.bin`, датасет ECO или API Lichess), которых в
проекте пока нет.

**Обход / текущее поведение.** Двухступенчатая схема: заголовок `[ECO]`
→ курируемая таблица префиксов → `None`. `None` означает «не знаю»,
догадка по первому ходу не подставляется. Таблица покрывает популярные
дебюты (Ruy Lopez, Sicilian, French, Caro-Kann, Nimzo, KID, Grünfeld,
QGD, Slav, English и др.).

**План закрытия.** T-017 (RAG/ingest): подключить полиглот-книгу или
офлайн-каталог ECO, заменить таблицу полноценным классификатором,
добавить детект транспозиций относительно книги. Тогда таблицу удалить,
тесты `test_eco_*` переписать на новый источник.

## KI-012 · Open · Med · ingestion

**Симптом.** `parse_pgn("1. e4 e5 2. Zz9 *")` возвращает партию из
**двух** ходов без единой ошибки: `python-chess` останавливает разбор на
токене, который не является валидным SAN, и молча отбрасывает остаток
movetext-а. Для ingest-а это опаснее, чем явная ошибка: партия
«тихо укорачивается», и анализ идёт по неполным данным.

**Причина.** Поведение парсера `chess.pgn.read_game`: нераспознанный
токен не попадает в `game.errors` (в отличие от нелегального, но
корректного по форме хода — например `1. e5` даёт `IllegalMoveError`).

**Обход / текущее поведение.** Ошибки «пустой PGN», «нет ходов» и
«нелегальный ход» ловятся (`InvalidPgnError`). Случай тихого обрыва
задокументирован тестом-маркером
`test_parse_pgn_unknown_token_is_rejected` (`xfail(strict=True)`): когда
поведение исправят, тест упадёт и напомнит обновить KI.

**План закрытия.** Перед `read_game` (или после) проверять, что весь
movetext разобран: сравнить количество SAN-токенов с числом полуходов
либо использовать собственный visitor, фиксирующий неизвестные токены.
Сделать в T-017 (массовый ingest) или раньше, если понадобится в API.

## KI-013 · Open · Low · engine, infra

**Симптом.** `STOCKFISH_HOST` / `STOCKFISH_PORT` в настройках и сервис
`stockfish` в `docker-compose.yml` (профиль `engine`, UCI-over-TCP) есть,
но `EngineService` их игнорирует: при заданном `STOCKFISH_HOST` и
отсутствующем локальном бинарнике выбрасывается `EngineNotFoundError` с
подсказкой про KI-013.

**Причина.** Реализован только запуск локального процесса
(`asyncio.create_subprocess_exec`). TCP-транспорт — отдельная работа
(сокет, переподключение, keep-alive, мультиплексирование клиентов).

**Обход / текущее поведение.** Только локальный бинарник
(`STOCKFISH_PATH` → `PATH`). Библиотека `stockfish` (py) остаётся в
зависимостях, но **не используется**: она не отдаёт PV-линии, нужные
`EngineLine`, и не даёт управляемых таймаутов. Это осознанный размен:
свой UCI-клиент (~250 строк) вместо приватного API библиотеки.

**План закрытия.** Вынести транспорт в `app/engine/transport.py`
(`LocalUciTransport` / `TcpUciTransport`) и выбирать по настройкам;
пригодится для пула движков в Docker (T-025) и горизонтального
масштабирования (SPEC §10). После этого решить судьбу зависимости
`stockfish` (использовать для TCP или удалить).

## KI-014 · Open · Med · engine, api

**Симптом.** `analyze_game_moves` на уровне «клуб» анализирует **каждую**
позицию (`N + 1` поисков по ~1 с). Для партии из 40 ходов это ≈ 41 с, а
SPEC §9 требует `/v1/analyze` ≤ 30 с (уровень «клуб»).

**Причина.** Оценка «до/после» берётся из отдельных поисков движка (по
одному на позицию). Это самый точный, но и самый дорогой способ; пула
движков и кэша пока нет.

**Обход / текущее поведение.** Для API (T-009) можно: понижать `movetime`
для длинных партий, анализировать только «критические» ходы или отдавать
результат стримом. Сейчас ничего из этого не сделано — ограничение
зафиксировано, а не спрятано.

**План закрытия.** Один или несколько из:
1) пул процессов Stockfish + `asyncio.gather` по позициям (главный
   кандидат: 4 воркера ≈ линейное ускорение);
2) кэш по `fen_hash` (`retrieval_cache` уже в схеме);
3) брать оценку сыгранного хода из MultiPV-линии позиции «до», если ход
   в неё попал (экономит второй поиск);
4) инкрементальный анализ: сначала дешёвая глубина, углубление только для
   `delta ≥ 200 cp`.
Проверить после T-009 (там появится реальный бюджет запроса).
