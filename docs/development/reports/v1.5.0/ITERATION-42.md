## 5. Что не так

| Ограничение | Детали |
| :--- | :--- |
| Полная backend-сюита локально не прогнана | Окружение нестандартное: PostgreSQL на 5437, Stockfish отсутствует в `PATH`; интеграционные тесты зависают. По указанию пользователя остановлены; полный прогон — на CI |
| Высокая доля битых PGN во внешнем корпусе | 7321 из 12 693 прочитанных (≈58 %) отброшены как `invalid_pgn`. Это свойство внешнего датасета, а не конвертера; PGN не «ремонтируются», чтобы не учить модель на нелегальных партиях |
| Нет анализа движка | Внешний PGN не содержит engine-оценок; `user` — только ходы и метаданные. Модель учится стилю комментария, но не связи «оценка → объяснение». Это осознанное ограничение T-087 |
| Человеческие комментарии шумные | Опечатки, обрывочные фразы, иногда несколько аннотаций подряд; дедупликация не выполняется, чтобы не терять разные аннотации |

| Сгенерированный датасет не коммитится | 39.2 МБ; `data/lora_gold_v1.jsonl` и `data/external_datasets/` в `.gitignore` |

## 7. Обоснование

- **Почему отдельный скрипт, а не расширение `generate_lora_dataset_from_db.py`.**
  T-080 читает PostgreSQL (`edits → commentaries → games`) и требует
  анализа ходов; T-087 читает внешний JSONL с PGN и не имеет ни БД, ни
  `edits`. Общий у них только контракт записи v2, поэтому конвертер
  переиспользует `build_fact_package`/`load_system_prompt`, а не
  дублирует SQL-пайплайн.
- **Почему `build_fact_package` получил `analyses=None`.** Это единственный
  способ сохранить один контракт «пакета фактов» для обоих источников.
  Пустой список нельзя молча подставлять: без анализа движка пакет не
  должен утверждать, что оценки проверены. Явная ветка с фразой «Анализ
  движка недоступен» честна и для модели, и для `train_lora` (маркеры
  `# Партия`/`# Ключевые моменты` остаются).
- **Почему не синтезируем `MoveAnalysis`.** Любая синтетическая оценка
  нарушила бы принцип «факты — от движка» (RULES §1) и научила бы модель
  выдумывать cp-оценки. Лучше дать меньше фактов, но только проверенных.
- **Почему чистим `[%eval]`/`[%clk]`.** Это служебные PGN-теги, а не текст
  комментария; в `assistant` они превращались бы в мусорные токены и
  провоцировали модель писать `[%eval ...]` в ответах.
- **Почему лимит 2000 символов и обрезка по слову.** Ограничивает длину
  `assistant` и стоимость обучения; обрезка по границе слова не оставляет
  «полуслова», а hard-cut нужен только для текста без пробелов.
- **Почему `--limit` ограничивает выход, а не вход.** Для обучения нужен
  предсказуемый размер датасета; сканирование идёт до набора лимита, а
  статистика показывает, сколько входных записей для этого понадобилось.
- **Почему битые PGN пропускаются, а не ремонтируются.** `python-chess`
  строг к нелегальным ходам; «ремонт» PGN рискует создать партию, которой
  не было. Счётчик `invalid_pgn` делает потери видимыми.
- **Почему нет дедупликации.** В корпусе встречаются одинаковые тексты с
  разными `id`; разные аннотации одной партии могут быть полезны. Дедуп не
  входил в постановку и мог бы скрыть долю повторов — его стоит добавлять
  отдельной задачей с явной политикой.
- **Почему `.gitignore`.** Входной корпус ~60 МБ и выходной JSONL ~39 МБ —
  это локальные данные, а не исходники; git не должен их хранить.
